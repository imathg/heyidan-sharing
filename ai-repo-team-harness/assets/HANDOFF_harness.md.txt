## 1. 定位

Fido Wiki 是主管 AutoWiki 在 Fido 场景下的 team-mode 落地。仓内 vendoring 主管 `autowiki/` 运行框架（只读机制），Fido 业务派生层放在 `fido_wiki/`，源数据放在 `source/` 与 `protocol/registry/`。

| 仓 / 包 | 角色 | 写入边界 |
|---|---|---|
| `autowiki/` | 主管通用 compile 工具：route 框架、merge、source_policy、indices | 只读 `source/` + 写 `out/` + `.autowiki/` |
| `fido_wiki/` | Fido 业务派生：routes（protocol / code / eval_method）、ingest（mcj / eval / snapshot / papers / paper-mentions）、discovery、prompts | Fido ingest 例外（specs/architecture.md I4）：派生 `source/_generated/**` 与 `source/fido-<ver>/<kind>.md` 两个 generated namespace；不写其他 source 路径 |
| `source/` | 团队事实输入（飞书、IM、妙记、paper 等抓取后的 blob） | 由 `lark-fetch` / `lark-im-fetch` / paper 通道写入；不接受手工编辑 |
| `protocol/registry/` | 五张结构化台账（exp / train / eval / ab / eval_session）| 由 `fido_wiki ingest` 系列子命令写入 |
| `out/` | 管理员 compile 后的对外分发 | 由 `autowiki compile` 写；事实错误回改源头 |

I4 边界：autowiki 完全不知任何 Fido 字段名；Fido 字段名只在 `fido_wiki/` + `.autowiki/config.yaml` 的 `route_extensions` 配置里出现。

## 2. Source Harness 设计契约

```text
维护者登记 seed → 抓 seed 本体 → 二次发现 manifest → 维护者确认 → 回填 activated_sources → 抓正文
```

| 文件 | 角色 |
|---|---|
| `source/sources.yaml` | 机器可读的 seed / discovery / activated 状态 |
| `source/SOURCES.md` / `source/SOURCE_INDEX.md` | 从 `sources.yaml` 派生的人读版盘点（由 `source-index` skill 重建） |
| `source/_meta/feishu/*.meta.json` | activated docs 的轻量指针索引；不含正文 |

边界：

1. `managed_seeds` 是入口；正式抓取队列写在 `activated_sources`。
2. IM 一次发现链路：抓 raw → 脱敏落仓 → 从对话正文抽飞书文档/妙记/论文/博客/网站链接 → 写 discovery manifest → 维护者确认后激活。
3. 只有 `activated_sources.docs` / `activated_sources.im_chats` / `activated_sources.papers` 才被 fetch 通道消费。
4. `meeting_queries` 用于补查命名归档；IM 一次发现以 seed 群聊正文为准。
5. compile 只读已激活 source blob 与 protocol registry，不从 seed 或 discovery 候选生成主线事实。
6. `technical_reference` / `business` 来源受 compile gate 约束：范围限定 reference 层（`paper` / `source` / `concept`），不作为 `model` / `problem` / `technique` / `meeting` 的 owner。

`activated_sources.docs` 终态：`{fetched: 164, excluded: 1}`，0 pending。Excluded 项是 IM 群「FIDO x 虚拟IP 评测」引用的 wiki token `HNNkwXXLSiMi9fkfK6hc1m0GnOg`，飞书 API 返回 `code=1310213 No view permission`；属 `technical_reference` 层，不影响 wiki 主线事实。

Reference 层 gate 验证：

```bash
python3 -m fido_wiki.discovery.check_reference_gate
```

`autowiki/source_policy.py` 已读 `source/sources.yaml` 的 `source_class` 与 `compile_gate`：

| route | 产出实体 | reference source 处理 |
|---|---|---|
| `release` | `model` / `problem` / `technique` | 跳过 |
| `meeting` | `meeting` / `problem` | 跳过 |
| `paper` | `paper` | 允许 |
| `protocol` / `code` / `eval_method` | `model` / `problem` / agent context | 不读 `source/sources.yaml`，不受 reference gate 影响 |

## 3. Protocol 维护备忘（fold from HANDOFF_protocol.md）

`protocol/` 是协议层第一手台账：`spec/`（schema）+ `registry/*.jsonl`（数据行）。维护者私有备忘在此固化为设计归档。

### 3.1 安全 reward 值域 — 两个口径分开

`train_registry.reward_stack[].range` 记的是 **整体安全 reward 值域**。源文档另有一套 **重点风险识别子项值域**，数字不同，逐版核对时别串。

| 版本 | 整体值域 | 源 | 重点风险子项 | 源 |
|---|---|---|---|---|
| fido-2.0 | `[-9,0]` | 2.0.md:201 | `[-6,0]` | 2.0.md:209 |
| fido-2.1 | `[-9,0]` | 2.1.md:186 | `[-6,0]` | 2.1.md:194 |
| fido-2.2 | `[-6,0]` | 2.2.md:194 | `[-4,0]` | 2.2.md:202 |

- 2.0 整体 `[-9,0]` 组成：QA 巡检 `[-1]` + 重点风险 `[-6]` + 底线 `[-1]` + 开源护栏 `[-1]`。
- 2.2 精细化打压同时动两处：整体 `[-9,0]→[-6,0]`、重点风险 `[-6,0]→[-4,0]`，子项标签 6→4，去 Qwen3Guard 护栏（2.2.md:91-92）。
- 早期样例台账把 2.1 整体值域误填 `[-6,0]` / 2.2 整体值域留空，已订正。

### 3.2 ep 逐行对，别跨行串

`ep` 是可重指部署槽，追溯模型只认 `mcj`。细节表里同一个 `ep` 跨行复用：

- `mcj-…fgf8g` 与 `mcj-…vzvmm` 共用 `ep-…gl6qs`（iteration.md:460-463 ↔ 596-600）。
- `mcj-…6rdm9` 的 ep 是 `ep-…5z6ms`（iteration.md:139-160），与 `ep-…gl6qs` 无关。

### 3.3 fido-2.2 安全配比文档自冲突

源文档自冲突：概述段（L87）"安全配比 1/4→1/5"，详细 Stage3（L191）"配比 1/4"。registry 取 `1/5`（`train_registry.安全配比` + `exp_registry.notes`）。复核以 1/5 为准，冲突归档在本节。

### 3.4 authority 字段已弃用

registry 是第一手台账，可信度由 `result_doc` / `artifact` 路径强弱 + `status` / `judgement` 成熟度承载，不需要三星制。`authority` 字段已整体删除（理由成文 `protocol/README.md §6`）。

### 3.5 PII / identity 边界

硬规则：git 中不保存 `name ↔ open_id` 映射。

| 内容类型 | 处理 |
|---|---|
| 正式文档、妙记、设计文档、分享材料 | 保留原文人名 |
| protocol registry | 内部共享可保留人名；`ou_` / `cli_` / `app_` token 不进入 |
| IM raw 暂存 | 写入 `source/_im/_raw/`，gitignored |
| IM 提交产物 | 只替换 open_id 关联的发言人身份为 `成员-<4hex>`；不清理话题、群名、代码标识 |
| 本地映射和 salt | 只留 gitignored 文件 |

### 3.6 评测链路改造（2026-06-12 起，活跃工作流）

跨仓单一设计源：`fido_cc/docs/design/eval-chain-design.md`（诊断／两阶段通道方针／七个工作包／执行编排）。本仓涉及：WP1 ingest 扩展消费期文档内嵌 sheet CSV（`fido_wiki/ingest/eval_registry.py`，staging＋人工确认，不直写 registry）、WP2 `protocol/tools/validate_registry.py` 撞键退化保护、WP3 `protocol/spec/eval_session_spec.md` 口径模板节。撞键规则权威文本在设计源 §5.2，两仓一字一致，不在本仓另行措辞。

## 4. Schema v2「主实验组」字段（已实施，fold from HANDOFF_main_group.md）

触发：用户问"现在因为我们回补了非常多的临时实验的分支，我们的 Registry 里面有没有字段能够拿到主实验组啊？"

### 4.1 已落地实现

`train_registry` 在 v1 基础上新增三字段：

```jsonc
{
  // v1 fields ...
  "experiment_group": "fido-2.3#table-2",    // <doc-stem>#table-<N>，与 lark-table 1:1
  "arm_label":        "v1",                  // 原文「实验编号」列
  "role":             "main"                 // enum {main, baseline, candidate, ablation, sidearm}
}
```

当前 `train_registry.jsonl` 共 434 行，其中 139 行 `schema_version=train_schema_v2`，含 v2 字段；295 行 legacy v1 不带（含 fido-1.x 4 行 `legacy_recipe` 与冷启回填行）。

### 4.2 role 推断 heuristic（已写入 `fido_wiki/ingest/eval_registry.py`）

| arm_label 形态 / 说明列 | role |
|---|---|
| `v0` 或「基线」/「previous」/「上一版」 | `baseline` |
| `produce ep` 非空 + 同 mcj 在 release.md 出现，或说明含「上线」/「推全」 | `main` |
| `v\d+[a-z]+`（后缀字母）+ 说明含「消融」/「ablation」/「去 *」 | `ablation` |
| mcj 同时出现在另一张表（分支表 / 多轮 RL 专项表） | `sidearm` |
| 以上都不匹配 | `candidate`（默认） |

### 4.3 推迟到 v3

| 字段 | 用途 |
|---|---|
| `parent_mcj` | 跨版本血缘（指向上一版 main 的 mcj_id） |
| `mcj_aliases[]` | 同 mcj 在不同表的别名收集（v1 / V1 / v1主线 typo cleanup） |
| `produce_ep_status` | 上线生命周期 enum（`planned` / `built` / `released` / `deprecated`） |

## 8. 残留 harness 静态约束（H 系列）

| 编号 | 项目 | 当前判断 | 后续动作 |
|---|---|---|---|
| H1 | `parse_source` 缓存键只含路径 | 继承自主管引擎；第二次 compile 原地改 source 时可能读旧缓存 | 评估把内容哈希纳入缓存键 |
